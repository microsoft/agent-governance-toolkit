# Jest 30.5.2 update for the SDK and Copilot extension

## Which dependencies changed and why

Replacement for Dependabot PR #4118, original head
`8868504e4c39edf4d43cb8c77fc02083121aab7f`. Both
`agent-governance-typescript` and
`agent-governance-python/agent-os/extensions/copilot` update the exact Jest
development dependency from `30.4.2` to `30.5.2`. No other direct dependencies
change. Jest's matching internal packages, new file watcher, resolver,
source-map implementation, and transitive dependency graph change with it.
Official release notes:
`https://github.com/jestjs/jest/releases/tag/v30.5.2`.

At initial regeneration, the original merge-base and main `17595e64` had
identical manifests and lockfiles for both packages. The reviewed original public-registry lockfiles
were regenerated with
`npm install --package-lock-only --ignore-scripts --legacy-peer-deps --offline --no-audit --no-fund`.
This preserved canonical registry URLs and upstream integrity metadata,
without discarding independent changes on main. Offline regeneration
establishes graph consistency, not independent registry verification.

Pre-install metadata review through the configured Microsoft mirror covered
all 123 changed package/version candidates. Each release was at least seven
days old; the youngest was approximately 8.37 days old at review. Jest
`30.5.2` was published on `2026-09-18T13:58:07Z`. The draft replacement's
hosted supply-chain run `37857591940` independently passed the seven-day
cooling-off and upstream lockfile integrity checks on its initial head.
Local canonical-registry checks failed closed on TLS handshake failures;
mirror metadata was not represented as an independent gate result.
The canonical release-age gate checked only the direct Jest identity, not
all 123 transitive release timestamps.

## Security advisory relevance

No known advisory addressed. This is a development-tool update, not a
security fix or a claim that the dependency tree is vulnerability-free.
The independent focused read-only review established no exploitable
vulnerability or malware, but that is not approval for lifecycle execution.
Its recommendation is **no execution approval and no current allowlist
exception**.

**The update remains blocked on an install-script policy decision.**
`jest-resolve@30.5.1` requires `unrs-resolver@^1.12.1`, replacing `^1.7.11`.
The SDK's existing resolver `1.11.1` is incompatible, so its regenerated
graph selects `1.12.2`. Both eligible `1.12.1` and `1.12.2` declare
`postinstall: node postinstall.js`. The Copilot lock already contains
`1.12.2`, but its presence is not evidence of security approval.
The baseline SDK resolver `1.11.1` also declared an installation script and
used helper `0.3.4`. This is a new artifact/version review, not the SDK's
first-ever lifecycle capability.

The independently verified chain is Jest `30.5.2` ->
`jest-resolve@30.5.1` -> `unrs-resolver@^1.12.1`, locked to `1.12.2` ->
`postinstall: node postinstall.js` ->
`napi-postinstall@0.3.4` calling
`checkAndPreparePackage(packageJson, true)`. The `true` argument checks
version consistency among declared optional bindings. The binding check
uses `require.resolve` to establish file existence, not a hash, signature,
or ABI load.

Distributed optional bindings normally resolve without a download. If a
binding is absent, the helper launches a shell command to install the
binding at `1.12.2` using npm with `--prefer-offline` and `--no-audit`.
It does not explicitly require `--ignore-scripts`, offline-only operation,
or reuse of the root lockfile. If that installation fails, it can download
a tarball, follow redirects including HTTP, and extract a `.node` or
`.wasm` file without SRI or signature validation. This is a demonstrated
trust-boundary risk; attacker control and an exploitable vulnerability
were not established. No lifecycle script was executed during the review.

The new `@parcel/watcher@2.6.0` declares an installation hook and is already
on the repository's existing allowlist. Its inspected hook builds only when
`npm_config_build_from_source` is explicitly true. No new exception,
incompatible override, scanner modification, feed setting, or TLS setting
was introduced. Shared candidate-cap fix #4151 is already merged; both the
original audit and the replacement's hosted audit use `--max-deps 2000`
and fail specifically on the SDK resolver postinstall.

### Maintainer-only proposal: not approved or implemented

The current scanner supports package-name and exact package/version
allowlists, but its exception branch skips the registry script query.
An existing test confirms this behavior. There is no YAML lifecycle
exception schema with an enforced expiry. Adding only an exact tuple
therefore does not meet this proposal's verification requirements.
The scanner/manifest trip-wire requires policy work in a **separate
maintainer-owned PR first**, not in this dependency branch.

For review only, consider a declaration-only decision for exactly
`unrs-resolver@1.12.2` and the entire lifecycle map
`{postinstall: 'node postinstall.js'}`. This would accept the reviewed
declaration, **not authorize execution**. Bind any decision to the
resolver SRI, entry point SHA256, helper `0.3.4` SRI, and exact native
binding identities and hashes in both reviewed lockfile graphs above.
Require canonical package identity and URLs, strong integrity, and
fail-closed verification; an exception must never skip verification.
Obtain verified exact-artifact provenance or explicitly escalate its
absence to maintainers.

Retain every `npm ci --ignore-scripts` installation and the normal
distributed optional bindings. Reject or disable unlocked missing-binding
recovery rather than authorizing the postinstall fallback. Any version,
lifecycle map, script, helper, artifact, graph, or platform change
invalidates the review. Do not assume an expiry mechanism already exists.
No proposed schema, verifier, exception, or recovery guard is shipped by
this document.

Required tests for any separate policy proposal, **not run or implemented
by this documentation update**:

- Accept only the exact reviewed declaration and artifact graph.
- Reject adjacent versions, added or changed lifecycle hooks, changed
  hashes, helpers, bindings, graphs, foreign alias URLs, weak SRI, and
  missing required provenance.
- Fail closed on registry TLS failures and unverifiable metadata.
- Retain coverage of all 123 dependency candidates and the existing
  scanner/manifest trip-wire.
- Reject removal of `--ignore-scripts` from CI installation commands.
- Demonstrate supported Node 20 Linux and Windows binding resolution with
  scripts disabled, and failure without recovery when a binding is absent.

The demonstrated safer alternative is the current script-disabled
installation, not postinstall approval. Maintainers may defer the update.
The draft remains blocked until an explicit policy decision and the
necessary separately reviewed implementation; this proposal does not
waive any required check.

## Breaking change risk assessment

Jest 30.5 changes module resolution, file crawling, watching, and source-map
handling. Neither package needed application or configuration changes.
Both clean installations used
`npm ci --ignore-scripts --legacy-peer-deps --no-audit --no-fund`; platform
bindings were available without running lifecycle scripts.

On Windows with Node `26.7.0` and npm `12.0.2`, both packages passed
`npm run build`, `npm test -- --runInBand --no-watchman`, and `npm run lint`,
all with exit code 0. Pretest typechecking also passed. The SDK passed 692
tests across 41 suites; the Copilot extension passed 13 tests across two
suites. Disabling Watchman exercises Jest's new crawler. The SDK emitted an
advisory asynchronous-open-handle warning but exited successfully; this
record does not claim to diagnose or fix that warning.

The initial hosted Node `20.20.2` SDK run failed one existing circuit-breaker
test because its real five-millisecond reset deadline expired between
assertions. A controlled ten-millisecond scheduling delay reproduced the
same assertion failure on both current-main Jest `30.4.2` and updated
Jest `30.5.2`, confirming fixture timing sensitivity rather than changed
production behavior. The fixture now uses a scoped fake clock, restores real
timers afterward, preserves every original state assertion, and additionally
checks that execution is blocked at four milliseconds and allowed exactly
at five milliseconds.

On checksum-verified official Node `20.20.2`, the corrected fixture passes
even with the same scheduling delay. Both package builds, pretest
type checks, full suites using `npm test -- --maxWorkers=2 --no-watchman`,
and lint pass with exit code 0. The SDK still reports an advisory worker
teardown warning while exiting successfully. No production behavior or
supported Node version was changed.

Hosted CI subsequently passed both Node 20 installation, build, and test
jobs in run `37858449141` for corrected head
`215fd9dd37f6b547cb07f7e8dae0954594ce8153`. Run `37858449180` also passed
upstream lockfile hashes and release age, and the dependency audit document
gate passed in run `37858449200`. The resolver postinstall policy check
still failed as expected. These results do not approve the script or replace
